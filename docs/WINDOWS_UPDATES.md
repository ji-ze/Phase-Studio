# Windows update provisioning and acceptance

This implementation is preproduction. `phase_studio/update_trust.py` currently
contains a public verification key; its presence does not prove that the
corresponding protected GitHub signing secret or production release is ready.
An empty trust map disables installation. Release notifications and the official
release page remain available. No production key is generated by building the
application or running GitHub Actions.

## One-time signing setup

For an installation without a provisioned key, an authorized release maintainer
runs the following in Windows PowerShell from
the repository. The new key directory must not already exist. Keep it outside
Git, OneDrive, build trees, screenshots and distribution folders. Never print
the private file, paste it into chat, or enable shell tracing for these commands.

The current source already has a pinned public key. Locate its matching private
key through the approved institutional secret store; do not generate a replacement
as a shortcut. If that key cannot be recovered, perform a separately reviewed key
rotation before signing releases. The commands below are for first provisioning,
not unattended rotation.

```powershell
$keyDirectory = Join-Path $env:USERPROFILE '.phase-studio-update-keys'
.\.venv-build\Scripts\python.exe packaging\tools\update_signing.py generate --directory $keyDirectory
if ($LASTEXITCODE) { throw 'Key provisioning failed.' }
.\.venv-build\Scripts\python.exe packaging\tools\update_signing.py pin-public --public-key (Join-Path $keyDirectory 'phase-studio-update-public.json')
if ($LASTEXITCODE) { throw 'Public-key provisioning failed.' }
```

The tool creates one raw Ed25519 seed encoded as base64, with a current-user
Windows ACL, and a separate public-key JSON file. It refuses an existing key
directory and refuses replacement of a different already provisioned public
key. Review and commit only `phase_studio/update_trust.py`. Back up the private
key in the institution's approved secret store. Key loss/rotation requires a
reviewed migration; never silently regenerate a key per build.

In GitHub repository Settings → Environments, create
`phase-studio-release-signing` and `phase-studio-release-publication`. Configure
required reviewers, prevent self-review, and restrict deployment branches to
protected `main`. Review the workflow on that branch before allowing secrets.
These controls are configured in GitHub; merely naming an environment in YAML
does not create those protections. See GitHub's
[environment protection documentation](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments).

After authenticating the GitHub CLI, upload the private key directly over stdin:

```powershell
Get-Content -Raw -LiteralPath (Join-Path $keyDirectory 'phase-studio-update-signing-key.txt') | gh secret set PHASE_STUDIO_UPDATE_SIGNING_KEY --repo ji-ze/Phase-Studio --env phase-studio-release-signing
if ($LASTEXITCODE) { throw 'Secret configuration failed.' }
```

Do not create a repository-wide copy of this secret. Do not supply it to the
build or publication job. The sign job alone receives it in one step.

## Release workflow

`.github/workflows/windows-release.yml` accepts a reviewed full source SHA
already integrated into `main`. It refuses an existing version tag. Its default
`publish: false` builds and signs artifacts without creating a tag or release.
Both packages, the helper and the public key come from the same source SHA.

The exact authenticated release boundary is six files:

1. `PhaseStudio-VERSION-x64.exe`
2. `PhaseStudio-Jana2020-VERSION.zip`
3. `SHA256SUMS.txt`
4. `release-manifest.json`
5. `release-manifest.sig`
6. `RELEASE_NOTES_VERSION.md` (dotted version)

The canonical manifest and detached Ed25519 signature authenticate both package
names, profiles, sizes, hashes and release version. Checksums alone do not
establish trust. Applications and the independent helper must embed identical
public keys. Never accept keys supplied by downloaded metadata.

Only an explicitly requested publication enters the separately protected job.
It creates a new tag and draft, uploads exactly those assets, downloads them
again, verifies them, and then publishes. A failure leaves a draft/tag for
maintainer review. Never force-replace a tag or existing release to retry.

## Installation and Jana2020 lifecycle

Downloads use public GitHub HTTPS requests, without SharpED credentials. The
user consents before downloading and again before closing the application.
Active scientific workflows block installation, including a second check after
helper readiness. The original executable filename and installation directory
are preserved. Preferences, credentials, projects, Superflip and EDMA are not
update payloads.

Jana ONEDIR updates replace only `Phase_studio.exe` and its complete owned
`_internal` runtime. An exact runtime inventory is mandatory. Unknown user files
or legacy installations trigger manual migration rather than deletion.
Standalone updates replace only the selected executable.

Direct Jana2020 launches use the explicit legacy fallback: cancel/close Phase
Studio, exit Jana2020, let the helper finish, then reopen Phase Studio from
Jana2020. The helper waits for the identified processes; it never kills Jana,
Superflip or EDMA, returns a candidate, or fabricates a handoff. It does not
restart an old `.inflip` invocation. This is not a claim that an automatic
resident Jana waiter/bootstrap has been implemented.

Protected installation directories require explicit Windows UAC. Plans are
bound to the current Windows user by DPAPI. Elevating with a different account
cannot decrypt them and must fail without replacement. A verified standalone
restart uses the original user's non-elevated token. The Windows API requires
appropriate process-token privileges; see
[CreateProcessWithTokenW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-createprocesswithtokenw).

## Recovery

The helper journals mutations beside the installation and retains original
files until the new runtime and, for standalone, visible startup are verified.
Handled failures roll back. After power loss or process termination, close all
instances and run `Recover update.cmd` in the matching private directory:

`%LOCALAPPDATA%\PhaseStudio\Updates\<session UUID>\`

Recovery revalidates the DPAPI plan, signature, payload and matching journal.
Never delete a pending journal or its backups to make an error disappear.
New installations refuse to start over an unfinished journal. If automatic
recovery cannot prove ownership/integrity, keep the backup and use an authorized
manual repair. Cached packages and diagnostic reports currently remain in the
private workspace for review; automatic age-based cache cleanup is not enabled.

## Activation checklist

- Provision the real key once; review the public fingerprint and source change.
- Configure protected environments and the signing secret.
- Build both profiles; run `packaging/tools/verify_update_build.py` against them.
- Complete disposable native Windows update, rollback, UAC, interruption and
  recovery acceptance for both packages, plus actual Jana close/reopen testing.
- Review real signed artifacts and downloaded copies before enabling publication.
- Manually upgrade existing pre-updater installations once.

Until these steps are complete, do not describe public automatic updates as
activated. Offscreen Qt screenshots and synthetic signatures verify only their
documented test scope, not a production identity or real Jana acceptance.
